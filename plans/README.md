## Hardening program objective

Plans 002–008 convert the 2026-08-06 repository assessment into one coherent
hardening program. The program protects the strongest parts of RSemble—one
provider-neutral pipeline, blind Judge evaluation, durable evidence, immutable
experiment provenance, and local-first operation—while repairing the boundaries
that currently lag behind those claims.

The mandatory sequence is:

```text
Decision lock
  → credential and bridge boundary hardening
  → run integrity and truthful preflight
  → deadlines and cross-tab execution leases
  → CI, lint, coverage, warning gates, and documentation
  → controlled structural extraction
  → measured loading and protocol compatibility
```

Later phases may be refined against live code, but they may not silently reverse
an earlier product decision or invariant. A reversal requires updating Plan 002,
`DECISIONS.md`, and every affected downstream plan first.

## Plan 002 locked decisions (D1–D6)

Plan 002 (`002-hardening-program-decisions.md`) is the program's decision gate.
It locks:

- **D1 Credential persistence** — environment variables preferred and read-only
  in the UI; UI keys session-only by default; per-key **Remember on this
  device** opt-in with same-origin/XSS disclosure; credentials never enter
  runs, logs, archives, exports, or fixtures; one shared `CredentialStore`.
- **D2 Compare cardinality** — Compare requires at least two enabled candidate
  slots before a paid run; single-model baselines exist only inside evaluation
  experiments that explicitly define them.
- **D3 Bridge authentication** — `RSEMBLE_BRIDGE_SECRET` is optional but
  enforced when set via `X-RSemble-Bridge-Secret`; `/health` public;
  `/auth/status` public metadata; protected routes fail
  `401 bridge_auth_required` / `bridge_auth_invalid`; loopback/CORS are
  defense-in-depth only.
- **D4 Attachment size authority** — 40 MiB raw aggregate UI limit; 64 MiB
  encoded bridge ceiling; encoded-size preflight for bridge-routed requests.
- **D5 Timeout semantics** — connect/header, stream inactivity, optional total
  ceiling, and user abort are distinct clocks; no single short wall-clock.
- **D6 Program ordering** — 002 → 008 in index order; no feature expansion in
  hardening pull requests.

Plans 003–008 may be refined against live code but **must not** reverse D1–D6
without updating this file and `DECISIONS.md` first.

## Cross-phase invariants

Every hardening phase must preserve these invariants unless the relevant
specification is deliberately amended:

1. **One pipeline** — task → parallel candidates → blind Judge → Rank/Fuse.
2. **Blindness** — RSemble-supplied model/provider identity never reaches the
   Judge or synthesizer before the documented reveal boundary.
3. **Evidence honesty** — missing usage, cost, outputs, or coverage remain
   missing/unknown rather than silently becoming zero or a fabricated estimate.
4. **Immutable provenance** — retries, repairs, roster extensions, and Fusion
   Study stages preserve exact source attempts and protocol identity.
5. **No hidden paid calls** — preflight, recovery, retry, and extension paths
   expose or deterministically derive the number of provider stages they execute.
6. **Credential containment** — credentials, authorization headers, bridge
   secrets, and environment contents never enter runs, experiments, logs,
   archives, exports, screenshots, or CI artifacts.
7. **Atomic terminal evidence** — structural extraction may not split an existing
   atomic run/attempt commit boundary.
8. **Local-first scope** — no hosted multi-user proxy, account system, or public
   execution API is introduced by hardening work.
9. **Deterministic verification** — default CI and browser QA use mocks/fixtures,
   not live paid provider calls.
10. **Accessible controls** — hardening must not regress focus management,
    semantic HTML, reduced motion, keyboard operation, or minimum target sizes.

## Dependency notes

### Plan 001

Plan 001 is complete. Its roster-extension discriminants, snapshot rotation,
reuse provenance, suite synchronization, execution fencing, and deterministic QA
are baseline behavior. Hardening plans must not weaken or special-case them.

### Plan 002 → Plan 003

Plan 002 resolves policy contradictions before security code changes. Plan 003
must consume the accepted credential, bridge-secret, attachment-limit, and
Compare-cardinality decisions rather than inventing alternatives in code.

### Plan 003 → Plan 004

Plan 004 assumes provider errors are sanitized, credential resolution is
centralized, bridge routes are exact, and payload limits are coherent. This lets
run-integrity work reason about trusted error and transport contracts.

### Plan 004 → Plan 005

Plan 005 wraps time and concurrency boundaries around a centralized, truthful
Compare preflight and complete frozen run context. Deadline/lease work must not
redefine candidate count, reasoning policy, or usage provenance.

### Plan 005 → Plan 006

Plan 006 makes the hardened behavior enforceable in clean CI and reconciles docs
only after the behavior exists. Documentation should describe tested contracts,
not planned aspirations.

### Plan 006 → Plan 007

Plan 007 is intentionally delayed until characterization tests, coverage, lint,
and warning gates protect structural changes. Large files alone are not a reason
to refactor.

### Plan 007 → Plan 008

Plan 008 relies on stable module/route boundaries for useful bundle analysis and
protocol isolation. Performance work is measured last so it cannot displace
security, correctness, or reliability.

## Recommended pull-request boundaries

Use one draft PR per plan by default. Plan 007 should usually be split further by
its internal workstreams because each extraction must remain independently
reviewable. Do not combine Plans 003 and 004 merely because both touch provider
and executor files; their acceptance criteria and rollback boundaries differ.

Every PR description should include:

- plan/workstream implemented;
- drift reconciliation performed;
- affected invariants;
- tests and deterministic QA run;
- migration or backward-compatibility notes;
- paid-call impact;
- residual risk and explicit deferrals.

## Findings considered and rejected or deferred

- **Special-case aggregation or matrix rendering for roster extension**:
  rejected. Snapshot-derived roster/coverage remains authoritative.
- **Weaken missing-cell repair's roster/fingerprint guards**: rejected. Hardening
  must preserve the existing provenance boundary.
- **Automatic persistent UI credentials without opt-in**: rejected by the
  recommended Plan 002 decision. Persistent convenience must be explicit.
- **General single-model Compare mode**: rejected for this program. Explicit
  evaluation baselines remain the supported single-model policy.
- **One short timeout for all provider calls**: rejected. Connect, inactivity,
  total, and user-abort semantics are distinct.
- **Refactor every file above a line-count threshold**: rejected. Plan 007
  extracts stable responsibilities only.
- **Make bundle warnings a release blocker immediately**: deferred until Plan
  008 establishes repeatable measurements and realistic budgets.
- **Live provider integration tests in default CI**: rejected. Use deterministic
  contracts/fixtures; any paid smoke is opt-in and explicitly authorized.
- **OS keychain integration**: deferred. The current program establishes honest
  environment/session/remembered browser credential semantics first.
