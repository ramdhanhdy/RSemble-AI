What does an AI score actually mean?

A model takes a test and scores 85. That number feels solid, like a bathroom weight or a bank balance. But it is really shorthand for a dozen choices somebody made. What was on the test? Who marked it? Under what conditions? Answer the question again tomorrow and you might get a different number. This page walks you through how RSemble keeps those choices visible, so a score can be trusted instead of merely believed.

Here is the honest starting point. A single score does not tell you what a model can do. It tells you what it did, on these particular questions, under these particular conditions, marked by this particular marker. The moment you forget any of those three phrases, the number starts to lie to you. It starts sounding like a fact about the model, when it is really a fact about one narrow encounter.

RSemble's answer is not to throw scores away. It is to build a chain of evidence behind every score, so that each link can be inspected on its own. There are five links. To make them concrete, we will follow one real question through all five — a question taken from RSemble's own PulseFit test suite.

The whole page has one rule. Remember it and the rest follows. What a task asks for  ≠  what a model actually did  ≠  what the model is capable of

The diagram at the top of the page is your map. As you read, each link lights up and fills with a piece of our one example. Scroll on.

Link 1 of 5

First, pin down the question. Exactly.

You cannot fairly compare two students if the exam keeps changing between them. The same is true for AI. So before anything is scored, RSemble freezes the question — every word of the prompt, the data attached to it, and the rules for a correct answer. We call this frozen copy a . Freezing matters because AI models are extremely sensitive to small wording changes. Rewrite the same question slightly and you may get a different answer, and you have quietly changed the test.

Our example · a real PulseFit tasktask-pulsefit-funnel-truth

The task reads, in essence: "Our acquisition dashboard says our cost to win a customer is stable. Prove whether that's true, using the numbers below." Attached is a small table of ad spend, installs, and paying customers. A correct answer must spot that the dashboard is dividing by the wrong number.

$95cost per customer, before
$120cost per customer, now
+26%the real change the dashboard hides

The dashboard looks flat because it divides spend by installs (many of which cost nothing) instead of by paying customers. The question is now frozen with those exact numbers. Whatever any model does later, it will be answering this question — not some drifted cousin of it.

Freezing also gives the question a fingerprint. RSemble stores a checksum — a unique code computed from the question's exact content. If a single comma changes later, the fingerprint changes too, and everyone can see that the question is no longer the same one.

Think of it like sealing the exam paper in an envelope and signing the seal.

Why this is easy to get wrong

Most teams keep their questions inside whatever file they happen to run from. Edit the file and every past result suddenly points at a question that no longer exists. You cannot re-check old conclusions because the thing you were measuring has moved. The fix is to give every question its own identity and history, independent of any file that happens to contain it.

Spot the trapYou tweak a question's wording to fix a typo, then compare new scores to old ones. Sound or risky?

B is the careful answer. Models react to phrasing. A typo fix may be harmless — or it may shift results. Either way, the honest move is to record it as a new version of the question, keep the old one intact, and never blend the two as if they were one. That is exactly what a task version buys you.

Link 2 of 5

Next, keep the answer — the exact one, not a paraphrase.

When a model answers, RSemble saves that answer in full, along with everything needed to know how it was produced: which model, which settings, what it was given. We call one saved answer a . This matters because a model can answer the same question differently each time. Ask it three times and you may get three different memos. If you only kept the last one, or a summary, you have lost the ability to see how much the model varies.

Our example · the model's memoone generation, saved in full

A model answers the CAC question. RSemble stores the entire memo it wrote, plus: the model's name and version, the exact prompt it saw, and its generation settings. If anyone later asks "how did it reach that conclusion?", the full answer is right there — not a memory of it.

The trap hiding in this step

Because a model can produce several answers to the same question, it is tempting to count each one as fresh evidence. This is one of the most common mistakes in AI testing, so it gets its own trap below.

Spot the trapYou run a model on 20 questions, 3 times each, and keep all 60 answers. How much question coverage do you have?

B is right. Re-running the same question measures consistency, not breadth. You still only touched 20 questions. Counting 60 makes coverage look three times wider than it really is. Repeats are useful — they show how stable the model is — but they never add new questions. RSemble keeps the two ideas separate: repeats sharpen a measurement, they don't widen it.

Link 3 of 5

Then grade it — and know exactly who's grading.

Some answers can be checked by rules: the arithmetic is right or wrong, the number is correct or not. RSemble runs those checks automatically and they are rock-solid. But many answers need judgment — is the reasoning sound, is the advice sensible? For those, RSemble uses a marker: often another AI, asked to grade against a written rubric. Each recorded grade is an .

Our example · two kinds of gradingchecks vs. judgment

What a rule can check: did the answer compute $120 correctly? Did it spot the wrong denominator? These are yes/no and reliable.

What needs judgment: was the recommendation sensible? Was the memo clear to an executive? A marker grades these against a rubric — and that grade comes with a warning label, explained next.

The marker is fallible — treat it like a witness, not a verdict

Here is the subtle part. An AI marker is itself a model, with its own quirks. Research shows markers can change their grade if you show them the answers in a different order, or if one answer is formatted more cleanly. A marker can be consistent and still be wrong. So RSemble does not take a grade at face value. It asks three questions of every marker:

1 · Can it repeat itself?

Give it the same answer twice, and the answers in a different order. Do the grades hold, or do they wobble?

2 · Is it actually right?

Test it on answers whose quality is already known. Does it agree with human experts, beyond mere chance?

3 · Has it drifted?

A rubric or model gets updated and grades quietly shift. RSemble records the marker's version so old and new grades are never mixed by accident.

Spot the trapA marker grades the same answer higher when it's shown first than when it's shown second. What does that tell you?

B is right. The answer didn't change; only its position did. That means part of the grade is measuring the marker's habit, not the work. This is why RSemble checks markers against known answers and records conditions. A score built on an unchecked marker can be confidently wrong.

Link 4 of 5

Now compare — but only like with like.

Scores become meaningful when you put two models' answers side by side. RSemble's whole purpose is to discover which pairs of models combine well, so fair comparison is the point. But comparisons are only fair if both models faced the same questions, graded by the same marker, under the same conditions. This is why the earlier links matter: you can only compare cleanly if the question was frozen and the grading was recorded.

Our example · two models, one questionsame question · same marker · same conditions

Model A and Model B both answer the frozen CAC question. Both memos are checked by the same rule (did it get $120?) and the same marker (was the reasoning sound?). Because every condition matches, any difference in their grades is about the models — not about one of them getting an easier test or a kinder marker.

The trap hiding in comparison

The biggest over-reach happens here. It is natural to look at scores on a test and conclude something big about the model in general. But a test is only as wide as its questions.

Spot the trapModel A outscores Model B on 15 business-analytics questions. A colleague writes: "A is better at business analytics, full stop." Fair conclusion?

B is the honest answer. On these 15 questions, A did better — that's a real, defensible fact. But 15 questions are a small window onto a huge subject. Whether A is "better at business analytics" depends on how well those 15 represent the whole field, which nobody measured. RSemble keeps the safe conclusion ("A scored higher on this set") clearly separate from the big one ("A is better at the skill"), and labels which is which.

This distinction has two names in the source document, and they are worth knowing because they stop you fooling yourself. Results about the exact questions you ran are a . Statements about a broader skill are a , and they are only justified if you deliberately chose questions to represent that wider world.

Link 5 of 5

Finally, say only what the evidence supports.

The last link is a report. But notice what RSemble does not do here: it does not stamp "reasoning = 82" onto a model and store that as a fact. A number like that looks like a property the model carries around, like its weight. It isn't. It is a summary of specific encounters, and it is only true under the conditions of those encounters. So RSemble stores the raw evidence and produces a — a summary that always names the questions, the marker, and the conditions behind it.

Our example · what the report actually saysderived, always re-computable

Instead of: "Model A · business analytics: 82."
RSemble writes: "On the 15 PulseFit questions, graded by marker v3 with rule checks, Model A outscored Model B on 9 of 15. This is about this set, these conditions, this date. Re-run or re-grade and the report updates."

The second sentence is longer, but every word in it can be defended. That is the trade RSemble makes on purpose.

What a report should not say

"This model is good at reasoning." — a free-floating trait, detached from any specific test, marker, or moment.

What a report should say

"Under these conditions, on these questions, the evidence looked like this." — bounded, dated, and re-checkable.

And this closes the loop with the rule from the very top. A report can describe what a task asked for, what a model did, or what we infer it is capable of — but it must always say which of those three it is talking about. Blur them together and you get a number that feels like truth but is really one unrepeatable moment dressed up as a fact.

Putting it together

The five links, as one chain of custody.

Read back-to-front, the five links are a chain of custody for a conclusion — like a court keeping track of evidence so nothing is lost or tampered with along the way.

1 · The question

A task version — frozen, fingerprinted, never silently changed.

2 · The answer

A generation — the model's exact output and the conditions that made it.

3 · The grade

An observation — a recorded measurement, with the marker's reliability checked.

4 · The comparison

Like with like — same questions, same marker, same conditions.

5 · The claim

A capability report — derived, dated, and always honest about its own scope.

You may notice the technical document lists a few more pieces — manifests that group questions into named tests, and facets that label what kind of thinking a question needs. Those are refinements of links 1 and 4: a manifest is just a named bundle of frozen questions, and a facet is just a label that helps you group questions fairly. They don't add a new idea; they make the chain easier to manage as it grows.

A score is not a fact about a model. It is the end of a chain. Judge the chain, and the score takes care of itself. the idea in one line

Keep these words

The terms, in plain English.

The source document uses precise names. They are worth keeping, because each one names a real idea. Here they are without the jargon.

Task versionthe frozen question
The exact, unchangeable copy of a test question plus its data and grading rules. Has a fingerprint so any change is obvious.
Generationthe saved answer
One complete answer a model produced, kept word-for-word with the model and settings that produced it.
Observationthe recorded grade
One measurement of one answer by one marker. It is an event, not a fact about the model.
Manifesta named test
A bundle of frozen questions grouped together, so you can re-run or re-refer to the same test.
Faceta thinking-style label
A label describing what kind of work a question needs (math, judgment, writing). A useful hint, not a measurement of the model.
Fixed-suite descriptionthe narrow, solid claim
A statement that is only about the specific questions you ran. Defensible but limited.
Population claimthe wide, risky claim
A statement about a whole skill or category. Only justified if your questions were chosen to represent it.
Capability reportthe honest summary
A summary computed from stored evidence. Names its questions, marker, and conditions; updates when the evidence does.
