1

The Big Idea

RSemble should move toward task-first storage — but should not remove suites. The recommended architecture layers four kinds of records, each with a distinct job:

canonical
Task Catalog → immutable Task Versions
The reusable library of work. A task exists once, with identity, and every revision creates a new immutable version.
protocol
Suite / Workload Manifest
A versioned selection of task versions plus an evaluation protocol. The UI keeps calling this a suite; internally it is a reproducible recipe.
frozen
Experiment
Freezes a suite version and execution configuration into a materialized snapshot, so history survives later catalog edits.
evidence
Task Observations
One model/policy/replicate measured on one task version or instance. The smallest reproducible unit of evidence.

The central design rule, straight from the document:

Store tasks and evidence at the smallest reproducible unit available, but aggregate only at the unit justified by the statistical question.

Which concretely means:

UnitRole
Raw evidenceobservation or attempt
Statistical generalizationthe task
Comparisonpaired task-level delta
Workload / protocolsuite version
Studyexperiment or trial

And the single invariant the entire design protects:

declares
A task has demands
→
produces
A model produces evidence
→
inferred
Capability is inferred
Why this invariant matters

A successful execution path does not reveal every skill a task requires. A model may use extra tools, take an inefficient route, or exploit an incidental affordance. Conflating “what the task needs” with “what one model happened to do” is the root error this whole design exists to prevent.

2

Vocabulary: Task, Skill, Capability

These three words get conflated across every external framework. RSemble defines them explicitly, because the storage model is built on the distinctions:

ConceptRSemble meaning
TaskA concrete objective or executable workload at the chosen evaluation granularity
Task familyA reusable class of related task instances
Task instanceA concrete prompt, input, file set, dataset snapshot, or environment state
Skill demandA knowledge or procedure requirement associated with a task — an annotation on the task side
CapabilityAn ability inferred from performance across related observations — a derived property of the model side
CompetencyDemonstrated ability under a defined context, standard, and evidence protocol
ProcedureA method or sequence reusable to solve a task
OutcomeA property expected from the result (correctness, completeness…)
EvidenceOutput, trace, artifact, verifier result, score, or judge observation
SuiteA versioned collection of task versions plus an evaluation protocol

The load-bearing distinction is the one between skill demand and capability. Demand lives on the task (declared or annotated before anything runs). Capability lives on the model (derived only after evidence exists, and always with uncertainty and provenance attached). A model-profiling view — the idea from the vault notes — is only honest if it respects this direction of inference.

3

Why Task-First: The Current Diagnosis

The research is not a blank-slate redesign. It starts from what RSemble already does well and what structurally blocks the future:

What already works

  • Task-level execution exists. RunRecordV2 already represents one task execution with candidates, judge results, fusion results, and winner information.
  • The experiment state machine preserves task invariants: one active attempt at a time, retries append instead of mutating, selected attempts point at accepted evidence, snapshots stay stable, delayed writes are rejected through epochs and execution fences.
  • Fusion Study already treats the task as the generalization unit and stores per-task results.

What blocks

Task definition storage is still suite-owned: EvaluationSuite embeds tasks: EvaluationTask[], and ExperimentSnapshot copies those definitions into the experiment. The consequences:

  • the same task is duplicated across suites;
  • task identity is effectively suite-local;
  • cross-suite task analytics require reconstruction;
  • taxonomy assignments would be copied into suite blobs;
  • task revision and suite revision are hard to distinguish;
  • a task cannot naturally accumulate observations across workloads;
  • imported tasks and variants lack explicit lineage.
The framing

Moving task definitions toward canonical task versions would complete an existing conceptual distinction — execution is already task-level — rather than replace the current product thesis.

4

Theoretical Foundations

No reviewed framework is sufficient as RSemble’s complete taxonomy. The sources fall into three classes, and each contributes one durable idea. Expand any card to see what the framework actually is and — more importantly — what RSemble takes from it.

4.1 Cognitive & educational taxonomies

These answer: what kind of thinking does a task demand? They annotate intent — they never measure models.

educational Revised Bloom’s TaxonomyAnderson & Krathwohl, 2001 — two-dimensional: knowledge × cognitive process ▶

The 2001 revision made Bloom’s taxonomy two-dimensional. One axis is what is being thought about (the knowledge dimension — nouns), the other is how it is being thought about (the cognitive process dimension — verbs). The revision renamed the original nouns to verbs, and promoted Create above Evaluate at the top.

The taxonomy table — click a cell

Any objective is classified by its verb (column) and its noun (row). An objective can legitimately occupy multiple cells — “write compositions that analyze patterns” lands in both Analyze and Create.

Select a cell to see what that combination means and an example.
What RSemble takes from it Use Bloom for intended cognitive demand and knowledge type — an annotation on the task, declared by the author. Never treat a Bloom level as empirical difficulty, and never as measured model capability. “Evaluate” on the task side says nothing about whether a model actually can.
educational Webb’s Depth of Knowledge (DOK)Norman Webb, late 1990s — complexity of engagement, not difficulty ▶

DOK classifies the complexity of cognitive engagement a task requires. Its most important teaching is that complexity ≠ difficulty. The canonical example: coming up with the 37th digit of π is very difficult, but not complex. The levels act as ceilings, not steps — they say how deep the engagement goes, and what comes after the verb decides the level, not the verb itself. “Identify the circle in a group of shapes” and “identify a strategy for addressing attendance using data from multiple sources” use the same verb at completely different depths.

DOK 1recall
Recall & reproduce. Facts, definitions, terms, well-known procedures. One right answer. “What is the knowledge?”
DOK 2skills & concepts
Mental processing beyond the habitual. Deciding how to approach; compare, classify, organize, explain relationships. “How can the knowledge be used?”
DOK 3strategic thinking
Reasoning, planning, evidence. Non-routine problems; original conclusions; justifying an argument. “Why can the knowledge be used?”
DOK 4extended thinking
DOK-3 complexity plus extended, iterative time. Planning, developing, revising across days. A long project made of DOK-1 chores is not DOK 4. “How else can the knowledge be used?”
What RSemble takes from it Store cognitive_complexity separately from difficulty. They are different axes and collapse into a misleading number when merged — this is one of the nine facets in §5 and one of the nine listed risks.

4.2 Occupational & competency frameworks

These answer: how do you describe skills as durable, linkable, versioned concepts? Their value to RSemble is structural (identity, relations, provenance), not content — the research explicitly warns against wholesale import of their vocabularies.

occupational O*NETUS Dept. of Labor — separates characteristics, knowledge, skills, abilities, tasks, activities, context ▶

O*NET refuses to flatten work into one list. It keeps worker characteristics, knowledge, skills, abilities, tasks, work activities, work context, experience, and occupational requirements as separate structures. Crucially, its task records carry metadata about the rating itself: source, date, population, importance, level, and relevance. A “skill matters for this task” statement is always a claim made by someone, about some population, at some time.

What RSemble takes from it Model task-to-skill links as many-to-many relations with provenance and population context — never a single undifferentiated importance value. This becomes the task_skill relation shape in §6, with fields for annotator, confidence, rationale, and evidence reference.
occupational ESCOEuropean Commission — versioned, machine-readable, multilingual concept registry (v1.2.1) ▶

ESCO is the gold standard for durable concept identity: 13,485 knowledge/skill/competence concepts, each with a persistent URI, a preferred term and aliases in 27 languages, a hierarchy (four sub-classifications: Knowledge, Skills, Attitudes & values, Language skills), and explicit relations. One honest limitation: it separates knowledge from skills/competences but draws no internal line between “skill” and “competence.”

What RSemble takes from it If RSemble ever imports external concepts, store the full reference — taxonomyNamespace, conceptUri, taxonomyVersion, preferredLabel, aliases, relationType. Never flatten an external taxonomy into unversioned local strings — that destroys the version and the ability to follow concept changes.
occupational SFIASkills Framework for the Information Age — skills × responsibility levels ▶

SFIA splits professional description into skills on one axis and responsibility levels on the other — where responsibility is composed of autonomy, influence, complexity, knowledge, and behavior. The lesson: proficiency is not one-dimensional “knows more.” Two people with the same skill can differ profoundly in how much ambiguity, judgment, and ownership they can carry.

What RSemble takes from it A conceptual reference for agent autonomy — autonomy, complexity, and judgment are legitimate axes of an evaluation story. But SFIA must never become a direct RSemble score scale; it was built for people in jobs, not models on tasks.
occupational DigComp & UNESCO AI Competency Frameworkcross-cutting concerns as first-class dimensions ▶

DigComp models digital competence as knowledge, skills, and attitudes spread across five areas — information/data literacy, communication, content creation, safety, and problem solving. UNESCO’s AI framework combines human-centeredness, ethics, AI techniques, and system design with Understand/Apply/Create progression. Both treat things like safety, ethics, and source evaluation as named dimensions in their own right, not footnotes on technical skill.

What RSemble takes from it Cross-cutting concerns — safety, ethics, privacy, human-centeredness, source evaluation — should be represented as independent facets or desiderata, never hidden inside a general technical-skill label.

4.3 AI benchmark & agent-evaluation taxonomies

These answer: how do you actually annotate and structure evaluation tasks for models? This is where the strongest practical patterns come from.

ai eval HELMStanford CRFM — Holistic Evaluation of Language Models: scenarios × metrics ▶

HELM’s contribution is making the evaluation design space explicit. A scenario is a triple — (task, domain, language) — and a metric is a desideratum: accuracy, calibration, robustness, fairness, bias, toxicity, efficiency. A run is a (scenario, adaptation, metric) triple. HELM measured 98 of the 112 possible core scenario×metric pairs — and the pairs it could not measure were recorded as such. “Not measured” is a representable state, not a silent gap.

What RSemble takes from it Task, domain, language, metric, adaptation/scaffold, and risk desideratum must remain separate entities. A result exists per task/metric pair where appropriate, and absence of measurement is data too.
ai eval BIG-bench200+ collaborative tasks — overlapping keyword ontology ▶

BIG-bench tags tasks with overlapping keywords spanning capabilities, domains, interaction mechanics, formats, stressors, and out-of-distribution behavior. One task legitimately carries many tags. Its history also carries a warning: the public task count changed between the paper and the repository releases — rosters drift.

What RSemble takes from it Use many-to-many tags with a tag_type, and version the taxonomy and the benchmark release separately. Never treat a keyword count or a roster as permanent.
ai eval Super-NaturalInstructions1,600+ expert-written NLP tasks across 76 languages ▶

A large collection of expert-written tasks annotated with task type, language, and domain. Its research purpose — studying generalization to unseen task types — is only possible because task type is an explicit, separable facet rather than something buried in the prompt text.

What RSemble takes from it Task type, language, domain, input/output granularity, and split role should be separate facets. You cannot ask “does this model generalize to new task types?” unless task type is a first-class field.
ai eval GAIAgeneral AI assistants — reasoning, browsing, coding, tools, files ▶

GAIA tasks combine reasoning, browsing, coding, tool use, and file/multimodal handling, with difficulty levels partly based on annotator estimates of steps and tools. But the benchmark makes a philosophically important refusal: it does not claim that one successful solution path reveals a complete capability decomposition.

What RSemble takes from it Store intended capabilities and observed execution paths separately (§6 keeps an intended graph and an observed trace as distinct records). Step counts and tool counts are path observations, not universal task requirements.
ai eval SkillsBenchBenchFlow — 87 tasks, 8 domains, controlled taxonomy enforced by a linter ▶

The most directly reusable pattern in the survey. SkillsBench’s core question — do reusable Skills improve agent performance across domains? — requires category to be a clean explanatory variable. Before the taxonomy, 87 tasks carried ~60 free-text categories that mixed domains (“finance”), operations (“Code Translation”), modalities (“spreadsheet”), and tool names (“flink”). The fix: a controlled vocabulary with separated axes — category (one value: the primary domain of procedural expertise), plus task_type, modality, interface, skill_type, difficulty (easy ≤60min / medium 1–4h / hard >4h for a median specialist), category_confidence, and optional secondary_category. Enforced by a CI linter against taxonomy.yaml, validated by two independent annotators with adjudicated disagreements.

What RSemble takes from it Called out by name as a strong practical pattern for RSemble’s first taxonomy implementation. Reuse the separation of axes and the discipline (controlled vocabulary, linting, independent annotation) — not the benchmark’s exact category labels.
ai eval ADeLeAnnotated-Demand-Levels — demand profiles for tasks, ability profiles for models (Nature, 2026) ▶

ADeLe is the most complete realization of the document’s core invariant. It annotates every task instance with 18 demand dimensions (rubrics for quantitative reasoning, logical reasoning, abstraction, identifying relevant information, critical thinking, calibrating knowns/unknowns, mind modelling, attention, five knowledge domains, atypicality, volume — plus algorithmic unguessability). Running a model over the battery yields per-dimension characteristic curves — success rate declining as demand rises — whose area becomes an ability estimate. Demand levels belong to tasks; ability levels belong to models; the two are non-populational (estimated from a single system, independent of other models).

Its explanatory power is concrete: a model scores 90.5% on GSM8K but only 59.1% on OlymMATH-Easy and 13.3% on OlymMATH-Hard — all marketed as “math reasoning” — because the demand profiles differ on quantitative/logical/inductive axes. GPQA underperforms despite easier reasoning demands because of low specificity: it quietly demands natural- and applied-science knowledge.

What RSemble takes from it Demand annotation belongs to tasks. Model capability estimates belong to derived analysis over observations, and they require uncertainty and provenance. ADeLe also shows demand-based features predict out-of-distribution performance better than embedding or fine-tuned assessors — the long-term payoff of doing task annotation properly.
ai eval Agent Skills specificationskill as packaged artifact — deliberately not a capability taxonomy ▶

The Agent Skills spec packages procedural knowledge as a directory — instructions, scripts, references, assets. It is a supply-side artifact format: something you hand to an agent. It says nothing about what a task demands or what a model can do.

What RSemble takes from it Keep three different “skill” concepts apart: skill packages supplied to an agent, skill demands annotated on tasks, and capabilities inferred from performance. They share a word and almost nothing else.

Facets, Not a Tree

The research’s strongest structural claim: a single universal skill hierarchy is not appropriate. Tasks are genuinely multi-dimensional, and forcing them into one tree either duplicates the tree per context or loses information. The alternative is orthogonal, versioned facets with typed graph relations — a task simultaneously has a domain, an operation, a cognitive demand, a modality, an interface, and so on.

✗ one tree (rejected)
skills/ ├── engineering/ │ ├── software/ │ │ ├── debugging/ │ │ │ └── python-debugging/ │ │ └── data-cleaning/ │ └── … └── research/ └── …does a task that needs python debugging to clean research data go under engineering or research?
✓ orthogonal facets (proposed)
task: "clean this sensor CSV for the study" domain: research operation: transform, verify cognitive: application modality: CSV interface: python verification: schema validation difficulty: {declared, human-time, model-relative, …}

The nine facets

Hover the task below and toggle facet values — the point is that a task wears many labels at once, from independent vocabularies:

TASK · “Debug the failing payment webhook and fix the retry logic”

Each row is an independent controlled vocabulary. Relations between tasks (variant_of, derived_from, requires, prerequisite_of, holdout_of, calibration_pair_for, …) are typed edges, not parent/child links.

Difficulty is not one number

The difficulty facet is itself multi-dimensional, stored as separate values: declared difficulty, cognitive complexity (Webb), operational complexity, human completion time, human success rate, model-relative difficulty, reliability threshold, and uncertainty. Collapsing these into a single “hard” label is one of the nine named risks.

The Storage Model

Five record families, each with a precise job. The discipline is in what each one refuses to do.

Task Catalog — Task + TaskVersion

A task has identity (taskId, lifecycle status, aliases, current version). Every revision produces an immutable TaskVersion: content hash, prompt, input/output contract, verification configuration, evaluation-profile reference, taxonomy assignments, difficulty metadata, source/author metadata, and a supersedes pointer.

Subtle point: task identity is not derived solely from prompt text. The same text with a different environment, scoring protocol, or source snapshot is a different task. The content hash is a deduplication and integrity aid — not the semantic identity.

Task families & instances — reserved now, used later

The current EvaluationTask is closest to a concrete executable task. The model reserves the distinction between a TaskFamily (reusable class of related workloads) and a TaskInstance (concrete prompt/input/files/environment snapshot) even though the first migration treats current tasks as both.

Suite as workload manifest — Suite + SuiteVersion + TaskMembership

A suite version references task versions and carries the protocol: model pool, judge configuration, evaluation profile, aggregation protocol, protocol fingerprint. Memberships carry context, not just an ID: order, stratum, weight, role, inclusion rationale, holdout/calibration designation. The UI keeps saying “suite”; internally it is a reproducible selection over canonical tasks.

Experiment — frozen for reproducibility

References a suite version and keeps a materialized snapshot even after canonical task records evolve. Historical results must stay independent of later catalog edits.

Task Observation — the evidence atom

One measurement: task version + instance + suite version + experiment + policy/treatment + model configuration + sample index + attempt index, plus outputs, score vector, verifier result, judge references, cost, latency, status, provenance. Attempts, retries, and remeasurements stay inspectable — a retry is not automatically a new independent treatment.

Intended graph vs. observed trace

For multi-step tasks, two separate structures: the intended graph (author-defined steps, dependencies, branches, loops, expected artifacts) and the observed trace (model actions, tool calls, intermediate artifacts, failures, actual timing). This is GAIA’s lesson made structural: one model’s solution path never becomes the assumed task decomposition.

The skill relation shape

Task-to-skill links are many-to-many records with full provenance (O*NET’s lesson):

FieldPurpose
task_idthe task side of the link
taxonomy_namespace + concept_uri + taxonomy_versionexternal concepts stay references (ESCO’s lesson) — never flattened strings
roletarget / required / supporting / constraint / observed
level_or_demandhow much of the skill the task needs
annotation_source, annotator, confidence, rationale, evidence_refwho said so, and why — labels are claims, not ground truth
required ≠ observed

The most important field is the role distinction. A tool or skill appearing in one successful trace is not necessarily required by the task. Marking an observed behavior as required is exactly the capability-conflation error from §1.

Evidence & Provenance

The research maps RSemble onto W3C PROV, the standard model of provenance. PROV says everything traceable decomposes into three kinds of things:

PROV conceptMeaningRSemble mapping
Entitiesthings that existtask definition, input files, source documents, model output, tool output, score, report
Activitiesthings that happentask execution, model generation, tool call, judge evaluation, verifier execution, aggregation
Agentsthings responsiblemodel, provider, human annotator, judge model, software version

And the operational rule — every score RSemble ever shows must be traceable to:

  • exact task/version and input snapshot;
  • model/provider/version;
  • prompt, scaffold, and tool configuration;
  • raw output and permitted trace artifacts;
  • scoring method and evaluator version;
  • human/reference answer or rubric;
  • provenance and timestamp;
  • uncertainty and known limitations.

The Statistics

Task-first storage exists to make honest statistics possible. Three ideas carry the weight.

8.1 Task-level independence

A suite with 20 tasks and three generations per task is not automatically 60 independent observations. Repeated generations estimate within-task variability — they do not create 60 independent workload draws. Try it:

20
3

The recipe for paired policy comparisons follows directly:

  1. keep repeated generations linked to their task;
  2. aggregate within task where appropriate;
  3. calculate paired policy deltas per task;
  4. bootstrap or permutation-test the task-level delta vector;
  5. report wins, ties, losses, uncertainty, cost, and practical thresholds.

8.2 Generalized accuracy — and why IRT is deferred

“Performance on this exact suite version” and “expected performance over a population of similar items” are different claims. The database must preserve enough structure to distinguish them. The classical tool for the second claim is Item Response Theory — worth understanding because the research explicitly defers it:

IRT in one picture

IRT models the probability of a correct response as a function of the model’s latent ability θ and the item’s difficulty b. In the simplest (Rasch) form: p(correct) = σ(θ − b). The 2PL form adds a discrimination parameter — how steeply the item separates strong from weak models. Ability estimates become item-free: comparable across different test sets.

The amber point is the item’s difficulty b: where the model has a 50/50 chance. Steeper curve = the item discriminates sharply between abilities. Move θ to read off any model’s success probability on this item.

So why defer it? Three reasons from the literature the research cites:

  • Regime mismatch. IRT estimators were built for human testing: hundreds-to-thousands of examinees, 20–100 items. AI evaluation inverts this — often fewer than 100 models against tens of thousands of items, with skewed or multimodal ability distributions. Classical estimators become computationally infeasible or unreliable there.
  • Sample-size floors. Item-parameter recovery is unreliable below roughly 30 models and only stabilizes around ≥100. RSemble’s model pool is far below that today.
  • It is genuinely worth waiting for. AI evaluation has one advantage human testing lacks: a stateless model can answer the same item repeatedly, so response probabilities are directly observable and the measurement axioms (additive conjoint structure, the Rasch form) can be tested rather than assumed. When coverage and sample size justify it, IRT-style modeling becomes far more defensible for AI than it ever was for humans.
RSemble’s stance

Defer latent-ability modeling until the data justifies it — and meanwhile preserve the item-level structure (task versions × observations) that would make such modeling possible later. This is exactly why “full latent ability or IRT modeling before enough cross-task data exists” is on the do-not-implement-first list.

8.3 Fusion Study implications

The task remains the generalization unit for Fusion Study. Candidate generation, ranking, fusion, and refinement get compared on shared task evidence, reporting at minimum: per-task policy score, per-task paired delta, criterion-level score vector, verifier result where available, cost and latency, wins/ties/losses, uncertainty, and claim level. A suite aggregate is never sufficient evidence for a policy recommendation — and the existing Fusion Study separation of selection headroom vs. synthesis headroom stays intact.

Migration Roadmap

The safest migration is incremental — six phases, each additive, each gated on the stability of the one before:

1
Canonical task identity

Add task catalog records and immutable task versions while retaining the current embedded task representation. Nothing is removed; nothing breaks.

gate: identity exists alongside the status quo
2
Suite membership references

Allow suite versions to reference canonical task versions. Continue materializing full task snapshots for existing experiments and imports.

gate: old experiments still reproduce exactly
3
Task-level observation index

Index existing run records by task version, suite version, experiment, model, policy, sample, and attempt. Detailed artifacts stay in the existing run store.

gate: cross-suite task queries become possible
4
Initial faceted metadata

Start small — a controlled vocabulary for domain, taskType, modality, interface, skillType, verification, difficulty (the SkillsBench axis pattern). Detailed cognitive-demand annotation only after identity and observation layers are stable.

gate: vocabulary lints, annotators agree
5
Task analytics

Task-level views: model scores, policy wins/ties/losses, criterion-level error patterns, complementarity, synthesis headroom, taxonomy coverage, difficulty and uncertainty, suite membership comparisons.

gate: the transposed ledger — the model-profiling idea becomes buildable
6
Capability analysis

Only after sufficient cross-task observations: broader capability profiles, as derived, versioned analyses — never mutable fields on model records.

gate: profiles carry uncertainty and provenance
The ordering principle

Identity first, then references, then indexing, then annotation, then analytics, then capability inference. Each phase earns the next. Capability estimation is last because it is the most inferential — the tip of the pyramid built on all the layers below.

Risks & Safeguards

The document closes with nine named risks, each paired with the safeguard that neutralizes it:

RiskSafeguard
One giant skill hierarchy becomes unmaintainableIndependent facets and typed relations
Taxonomy labels are mistaken for ground truthStore annotation source, confidence, rationale, and taxonomy version
Difficulty collapses into one misleading numberStore cognitive, operational, human, model-relative, and reliability dimensions separately
Observed tools are treated as required skillsKeep intended requirements separate from observed traces
Retries are counted as independent evidenceModel attempts, treatments, and remeasurements explicitly
Historical benchmark results silently changeVersion task rosters, taxonomies, suite manifests, and protocol fingerprints
Aggregate scores hide heterogeneous task behaviorPreserve task/item observations and report task-level uncertainty
External occupational taxonomies are over-appliedUse external schemes as references and mappings, not as the core ontology
Latent ability estimates are overinterpretedDefer IRT-style modeling until coverage and sample size justify it

And the explicit do-not-implement-first list

  • a single global skill tree;
  • a single scalar difficulty field;
  • global model rankings across unrelated suites;
  • full latent-ability / IRT modeling before enough cross-task data exists;
  • automatic skill inference treated as ground truth;
  • wholesale import of ESCO, O*NET, SFIA, ADeLe, or SkillsBench vocabularies.

What Comes Next

The research names its successor artifact explicitly:

The next reviewed design artifact should be the Task Catalog and Workload Manifest Specification.— closing recommendation of the research document

It must define ten things: task and task-version identity; task-family and task-instance boundaries; suite-version membership references; experiment snapshot rules; task observation indexing; taxonomy namespace and facet assignment contracts; verifier, judge, and score provenance; intended task graphs and observed traces; migration compatibility with current suite blobs and experiment snapshots; and acceptance tests for reproducibility and task-level aggregation.

And the sequencing note that matters most: the broader skill taxonomy and capability inference layer should follow this foundation, not precede it.

Connection to the vault ideas

This is the missing foundation flagged in the RSemble Model Add-On and Profiling idea note. Add-model-to-finished-run (idea 1) is observing a new model on existing task versions — it needs canonical task identity and the observation index (phases 1–3). Model profiling (idea 2) is capability analysis over accumulated observations — phase 6, the last thing built, and only honest because every layer beneath it preserves the task→evidence→capability direction of inference.
