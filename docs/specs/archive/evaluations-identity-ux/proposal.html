● RSemble AI · Evaluations UX proposal

Two lists. Same face.
That's the whole problem — and identity is the fix.

Suites and Profiles are two genuinely different things wearing one costume. This proposal makes them unmistakable, connects them visibly, and corrects the status vocabulary — without redesigning the app, adding routes, or adding animation.

Problem 1
Identical anatomy. Same row shape, same fields, same actions, same "vN" provenance. Nothing on either page says what kind of thing you're looking at.
Problem 2
The status tokens lie. Every profile shows emerald ✓ Completed — a run-lifecycle state — even though a rubric never "completes." Every suite shows Draft, even suites that are fully runnable and have been run before.
Problem 3
No connection shown. A suite pins a profile version as its judging rule, but no suite surface ever names it, and you can't tell from the list which suites use which rubrics.
Problem 4
The rows don't earn their space. Suites don't show whether they've ever been run. Profiles don't preview what they actually measure.

02 THE INSIGHT

They are different kinds of things

The data model already knows the difference. A suite is a workload you execute. A profile is a rubric that scores. The UI just never says so.

Suite = Workload

You run it

A versioned set of tasks, candidate models, and a judge. Executing it produces experiments — the model-by-task result matrices.

  • Containstasks, model slots, default judge, pinned evaluation
  • Verbrun · duplicate · archive
  • Producesexperiment snapshots with results
Profile = Rubric

It judges, it never runs

Scoring criteria with weights and 1/3/5 anchors, plus the instruction the judge model receives. Immutable per version, so old results stay auditable.

  • Containscriteria, weights, anchors, judge instruction
  • Verbedit as new version · pin · archive
  • Producesnothing by itself — it is consumed by suites

one direction only · suites consume profiles · a profile never knows about suites

The fix in one line: give every surface a kind label (Workload / Rubric), give each kind an honest status (Ready / Reusable), and make the pin relationship visible in both directions. Everything else follows.

04 THE RELATIONSHIP, MADE VISIBLE

One pin, two directions

The data model already stores everything needed — no new storage, no migration. Both directions become derived, read-only, tested joins.

Suite → Profile
Every suite row and the suite editor header show a chip naming the pinned rubric — ⚖ Clarity rubric v3 — linking to the profile. Holistic suites show a muted "Holistic judging" chip. A missing pinned profile surfaces honestly as "Rubric missing."
Profile → Suites
ProfileDetail already lists suites pinned to the selected version — that logic gets extracted into a tested profile-usage module and gains one missing piece: suites pinned at other versions, so v2's page can warn you a suite still pins v1.

05 THE FOUR UPGRADES

What changes, precisely

U1 Entity grammar — every record says what it is

BeforeRows carry only name + version + timestamp. Nothing distinguishes the two kinds.
→
AfterAn 11px eyebrow on every record: ⠿ WORKLOAD or ⚖ RUBRIC, with the one-line definition available as a tooltip. Same eyebrow on rows, headers, chips, backlinks.

U2 Honest status vocabulary — two new tokens, nothing repurposed

BeforeSuites: ✎ Draft (all of them). Profiles: ✓ Completed (all of them). Run-lifecycle words on things that don't run.
→
AfterSuites: ▶ Ready (cyan) — a runnable workload. Profiles: ◉ Reusable (zinc) — a live, pinnable rubric. Archived keeps Aborted. Runs vocabulary untouched.

U3 Relationships surfaced both ways

BeforeSuite never names its rubric. Profile shows only same-version backlinks, via an untested inline function.
→
AfterSuite rows + editor show the pinned-rubric chip. Profile detail shows all pinning suites, including other versions, via a shared tested profile-usage module.

U4 Rows earn their space

BeforeSuite row: 3 tasks. Profile row: 4 criteria. No signal about runs or what the rubric measures.
→
AfterSuite row: 3 tasks · 4 models · rubric chip · last run ✓ 2h ago. Profile row: 4 criteria · Accuracy +3 more · pinned by 1 suite.

06 MOTION DISCIPLINE

The audit said: add almost nothing

A full sweep of the codebase found zero motion violations — no transition: all, no UI ease-in, no scale(0) entrances. The existing tokens stay the only motion vocabulary. Every candidate went through the four-question gate (frequency · purpose · speed · function):

CandidateGate resultVerdict
Segmented nav active swapState indication · tens/day · color onlyKeep — 150ms color transition
"Used by" disclosure openPreventing jarring change · occasionalKeep — opacity only, stable height
Archive-confirm arm swapGeometry must not shift · occasionalKeep — fixed action-cluster width
Row hover lift / transformHigh frequency · data rows must not moveReject — color-only hover, forever
Row entrance stagger on loadEvery navigation · rows are read, not watchedReject — too frequent
Sliding indicator between tabsDecoration · color state already sufficesReject — no purpose
FLIP reorder on filter/sortDESIGN.md forbids animating row positionsReject — settled decision
Kind-glyph morphing"It looks cool" is not a purposeReject — decorative

This is the Emil Kowalski filter in action: in a dense daily tool, the strongest move is usually deleting motion or not adding it. The upgrade's lever is identity, not animation.

08 SCOPE FENCE

What this deliberately does not touch

  • No route or navigation restructure — the Suites | Profiles tabs stay; only labels gain sublabels.
  • No storage migration — backlinks are derived by scanning existing records.
  • No task-first taxonomy — that research stays research; schemas are unchanged.
  • No new dependencies — lucide-react, Base UI, and cmdk already cover everything.
  • No Compare or Runs behavior change — shared primitives only gain optional, backward-compatible slots.
  • No new animation library or entrance effects — the motion audit said the discipline is already right.
